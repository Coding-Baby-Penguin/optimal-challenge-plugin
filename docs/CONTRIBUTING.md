# Contributing and recovery

Use CPython 3.12 and the hashes in [`requirements-dev.lock`](../requirements-dev.lock). In a clean virtual environment, install with `python -m pip install --require-hashes --only-binary=:all: -r requirements-dev.lock`. The hosted matrix uses Python 3.12.10 on Ubuntu 24.04 and Windows 2025. The lock covers the direct and transitive development dependencies; production scripts use the Python standard library.

From the repository root, run `python scripts/check_quality.py --mode structural --output tmp/quality/summary.json`. Read the JSON summary and the named `tmp/quality/check-*.log` files; a failed, blocked or zero-test check is not success. The same structural command runs in the pinned-action hosted matrix. `python scripts/validate.py` runs the integrated content/schema/scenario checks alone. Run `python -m unittest discover -v` when editing a focused owner; use the relevant `tests/validation/test_*.py` module during RED/GREEN work, then run the full structural gate.

If the structural gate fails, open `tmp/quality/summary.json` first. A `structural.status` of `blocked` points to Python or dependency prerequisites in `structural.reasons`; otherwise find each non-passing item in `checks` and open its `log` path. The `links-lf-secrets` check reports failures in its `reasons` array instead of a log. For `unit`, confirm `observed_tests` is greater than zero. Fix the named cause and rerun the full structural command; a `host.status` of `unverified` is expected in structural mode.

[ARCHITECTURE.md](ARCHITECTURE.md) identifies the owner of each behavior. Keep `scripts/orchestration_state.py`, `scripts/capability_matrix.py` and `scripts/evaluate_behavior.py` as compatibility facades and preserve public signatures, proof-class identity and CLI exit codes. Update the owning module and its consumer tests, then run full discovery after each ownership migration. For file moves, use [the exact move map](maintenance/folder-plan.md) to check imports, command paths, config, manifests, package selection, CI and links. If a migration fails, restore the focused files together from the preceding local candidate commit and rerun the same gate; do not hide a partial result.

Policy pins protect stable guarantees, not the dated [project checkpoint](PROJECT-STATE.md). To change a stable contract, write a failing policy-mutation test, obtain review of the deliberate semantic change, update the exact pin/fixture identity, then rerun structural checks. A new fixture version never rewrites the historical baseline. Keep all fourteen rubric weights fixed, including the 20% cleanliness dimension. Record evidence identities and distinguish expected case calculations from observed host traces.

Before a release, inspect the staged file set, selected package members and archive SHA. `python scripts/package_release.py` builds a deterministic archive from selected Git-tracked files; its output is the immutable candidate identity. Extract it in a clean location and install that source in an isolated host home. A local marketplace install directly from a dirty checkout can copy ignored scratch and `.git`. Use `scripts/check_quality.py --mode release --evidence-root <path>` only with independently verified current host evidence; a structural pass, status text or synthetic JSON cannot unlock release. Validation-branch commits/CI are allowed for evidence collection; publication to `main` or a release remains gated by the approved plan and actual read-back.

Keep current state in [PROJECT-STATE.md](PROJECT-STATE.md), stable policy in `config/`, historical plans in `docs/superpowers/`, reviews in `docs/reviews/`, raw run/grade/receipt evidence in ignored `tests/results/<evaluation-id>/`, local state in ignored `.optimal-challenge/`, and temporary build/test output in ignored `tmp/quality/`. Share sanitized findings rather than raw credentials or private host data. If a prerequisite or host surface is unavailable, mark it blocked or unverified with the exact next action.
