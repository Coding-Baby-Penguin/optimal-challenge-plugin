Use `python scripts/review_acceptance.py --manifest <manifest> --baseline <bundle-A> --candidate <bundle-D> --baseline-receipt <receipt-A> --candidate-receipt <receipt-D> --audit <reviewed-audit> --evidence-root <local-root> --reviewer-id <independent-reviewer>` for the executable one-process comparison. A CLI process that merely reads a review-status JSON does not recreate process-local approval. The release gate stays blocked until current subject identities and the complete release evidence are independently verified.

This trust model assumes an honest local reviewer and caller, local files that are retained through comparison, and code in the verifier process that has not been compromised. Hashes detect drift and bind files; they are not signatures against hostile same-process code. An imported status string, copied fixture output, self-declared `usage.complete`, or synthetic native file without a real audited origin cannot establish host behavior. Failed/cancelled runs, missing child usage, incomplete tool streams, grader disagreement or an unsupported surface remain explicit failed/blocked/unverified records. Retention is opt-in to the named local directory; never upload raw rollouts or credentials to structural CI. Preserve a sanitized index of digests, statuses, limitations and next actions for review.

The issuance boundary still depends on an honest registered adapter and an actual observed executable stop handle; a caller-supplied `codex-host` string and allowlisted proof name in a unit fixture are insufficient.
